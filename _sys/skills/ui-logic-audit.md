# UI 逻辑审计：从「多套并行实现」收敛到单一框架

## 何时用

- 用户说某处**逻辑不对**、**有个没用的 tag/tab**、**点了没反应**、**同一面板行为前后不一致**、**某类页面缺入口**。
- 用户要求「**检查是否为统一框架**」「全部处理下所有页面的这个逻辑」。
- 你准备改动一个已有 UI 概念的渲染逻辑——先审计再动手，否则很容易在第二套语义上再叠第三套。

核心判断：**同一个概念若存在 >1 个状态变量、>1 个入口语义、>1 个渲染实现，就是逻辑错误的温床。** 症状通常不是"某个函数写错了"，而是"两种意图在互相覆盖"。

## 第一步：清点（先数，再改）

围绕该 UI 概念的**关键词**（tab 名、面板名、按钮文案、字段名）做全量检索，回答 7 问：

1. **状态变量有几个？** 同一个抽屉/面板是否被两个变量分别控制（例如一个管 tag、一个管视图模式）→ 二者一旦不同步，表现就是"点了没反应"。
2. **渲染出口有几个？** 是否每个入口各写一份渲染代码 → 输出格式逐渐分叉。
3. **入口有几种语义？** 同一个面板的多个入口，是否有的"切换"、有的"打开"、有的"总是打开" → 同一个按钮点击有时开有时关。
4. **计数/摘要与列表同源吗？** 标题里的数字是否用 `a.length || b.length` 这类"或"取值 → 两者都存在时数字与实际列表不一致。
5. **有没有"硬凑配对"？** 把两组数据按序号/索引对齐（例如"第 N 条记录对应第 N 个快照"）→ 只要两组数据没有共同的时间戳或 ID，这种配对就是编造的，必须改成并列展示。
6. **入口的显示前提覆盖全部对象吗？** 例如依赖"页面里存在 H1"才渲染按钮 → 少数页面永远没有入口。凡按结构特征找挂载点，必须有**兜底落点**。
7. **切换对象后内容会刷新吗？** 面板开着时切换页面/条目，是否有重渲染钩子 → 否则残留上一个对象的内容。

顺手做一次**死实现清查**：被删/被替换的旧实现若仍留在文件里（函数、样式类），就是事实上的第二套语义，会被后续维护者误用。**先确认引用数为 0，再删。**

## 第二步：修复原则

1. **单一状态源**：一个概念一个变量（枚举值而非多个布尔）。所有入口只做一件事——设置它，然后调用唯一的渲染出口。
2. **唯一渲染出口**：一个函数按状态分派；分支内不重复实现共同的页头/容器。
3. **入口语义一致**：toggle 就是 toggle（开着再点=收起），"进入"就是"进入"。**不要让某条路径产生"用户没主动打开却被打开"的状态**——否则用户点按钮的第一下是"关闭"，表现为"点了没反应/反而关了"。
4. **不可得即留白**：状态无效时（未选中对象）该分支**置灰 + 给出提示**，不要静默失败，也不要渲染旧对象的内容。
5. **诚实计数**：数字只从实际要渲染的那份数据里取；数据无法关联就分节并列，不要编造配对关系。
6. **清理死实现**：删函数 + 删样式 + 删残留事件绑定，同一次改动内完成。
7. **给关键节点加稳定 id**（标题、计数、容器）：既方便断言，也避免后人再用"取 div 的第 2 个孩子"这种脆弱定位。

## 第三步：验证（真实浏览器断言，不靠肉眼）

用**无头 Chrome 加载真实构建产物**（`puppeteer-core` + 系统 Chrome 的 `executablePath`；静态单文件可直接 `file://` 加载），把每条修复写成**可断言的检查项**：

- **结构**：标签数量与文案、被删标签确实不存在。
- **状态**：初始态（未选中对象时该分支禁用）、非法切换被拒绝。
- **计数**：渲染出的条目数 === 数据源计算出的期望值（分别验证"记录数"与"附加快照数"）。
- **切换**：在 A 分支下切到 B 分支确实生效、再切回正确（**旧实现最常在这里失效**）。
- **对象跟随**：面板开着时切换对象，标题与内容实时跟随。
- **空态**：无数据对象的行为（不显示入口 / 显示空态文案）。
- **回归**：改动前已有的验证脚本必须仍通过。
- **零报错**：收集 `pageerror` + console error，必须为空。

同一套断言**至少跑两种视口**（桌面 + 移动），移动端另测：标签文案不被裁切、容器无横向溢出、长列表能滚到底。

把断言脚本留着：它同时是下一次改动的回归基线。

## 附：大文件（模板/构建产物）里 JS 语法错误的定位三招

`node --check` 对"少了闭合括号"只报 `Unexpected end of input`（位置在文件末尾，毫无指向性）。按顺序用：

1. **用 acorn 解析拿结构化信息**（一行命令）：
   `NODE_PATH=<node_modules> node -e "const a=require('acorn'),f=require('fs');a.parse(f.readFileSync(F),{ecmaVersion:2022})"`
2. **补括号试探 + AST 定位**：给源码末尾追加 n 个 `}` 再解析——某个 n 通过即说明只缺 n 个闭合；再遍历 AST 找 `end` 贴近文件末尾的节点 → 直接得到**未闭合的函数名与起始行**。这一步能省掉大半时间。
3. **拿构建产物当语法基准**：构建产物里的脚本是"真源 + 注入数据"，通常本身能通过解析；把它与当前源文件的脚本块 diff，即可把**自己刚引入的差异**从历史累积差异中隔离出来。注意先确认 diff 基准与真源版本一致（构建产物可能是旧版本），不一致时会得到误导性的长 diff。

## 红线

- 不要在旧实现旁边加新实现；改就替换干净。
- 不要为"看起来能用"而保留两套语义（例如同时保留自动打开与手动开关）。
- 不要用索引/序号配对没有共同键的两组数据。
- 不要把"内容是否变化"的判断写在文件首行——渲染管线可能不剥离 frontmatter，必须按**渲染后**的结果判断。
- 删代码前先验证引用数为 0，并在同一次改动内跑通回归。
