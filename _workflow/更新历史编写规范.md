# 更新历史编写规范（my-second-brain-v2）

> 本规范约束 `vault/更新记录/` 下所有更新记录 Markdown 的命名、frontmatter、标题、正文结构。
> 目的：统一格式，让 viewer 的「更新历史」抽屉 / 「页面更新历史」按钮 / 侧边栏标签稳定可用。
> 生效：2026-07-29 起，所有新写与重写的历史均按此执行（旧 1-19 次已批量归一）。

---

## 一、适用对象与存放位置

- 所有更新记录放在 **`vault/更新记录/`**，文件名 `YYYY-MM-DD_第N次更新.md`。
- **不要把非更新记录文件放进此目录**——`convert.py` 的 `parse_update_records` 会把目录下每个 `*.md` 当成一条记录解析，污染抽屉。
- 本规范等说明文档放 `_workflow/`，不放 `更新记录/`。

## 二、文件命名

- 格式：`YYYY-MM-DD_第N次更新.md`
- 第 N 次为**连续整数**，从 1 开始递增。
- **某次记录原始缺失时，保留空缺、不重排**（重排会改变 slug，断 wikilink / bundle 引用）。
  当前缺口：**第 15 次**（原始记录缺失，已在下方登记，不补空内容）。
- 部署：`bash deploy.sh "第N次更新：一句话"` 会自动把本次提交解析进「应用更新记录」页。

## 三、Frontmatter（唯一合法格式）

```yaml
---
tags: [更新记录]
created: YYYY-MM-DD          # 必填，ISO 日期（与文件名日期一致）
importance: 1-5              # 必填，唯一整数；禁止写 normal/low/high/medium
更新类型: 内容消化|站点优化|重大重构|例行维护   # 四选一，禁止混用其他词
---
```

### importance 1-5 定义（每级包含什么）

| 等级 | 标签 | 包含的内容 |
|---|---|---|
| 5 | 必看 | 高确定性 + 高影响；或本次主线核心标的 / 主题。不读会漏掉关键变化。 |
| 4 | 重要 | 结构性变化，值得优先看（建议读）。如目录重构、主线标的逻辑调整。 |
| 3 | 有价值 | 补充视角 / 可执行的细分框架。单篇深挖、细分行业补全。 |
| 2 | 常规 | 偏观察、单点信息。单条素材消化、小幅修正。 |
| 1 | 次要 | 边缘或纯存档。格式校准、去重、断链修复。 |

### 更新类型枚举（四选一）

- **内容消化**：把新素材（inbox / 链接 / PDF）消化进 wiki，新增或扩写页面。
- **站点优化**：viewer / 前端 / 构建逻辑等技术改动（纯技术，不含投资观点变化）。
- **重大重构**：目录结构、架构、组织方式调整（如合并 S1-S5 到策略专题）。
- **例行维护**：修断链、去重、统计校准、格式统一等可用性维护。

## 四、标题行（唯一合法格式）

```
# 第N次更新 | YYYY-MM-DD | 一句话概述
```

- 三段用 ` | ` 分隔：**第N次更新** | **日期** | **一句话概述**。
- 前两段必填；第三段「一句话」建议 10-20 字，概括本次核心。若确实无重点，第三段可省略，但不得把大段内容塞进标题（旧版第 12~16 次曾把内容写进标题，已纠正）。
- 日期必须出现：统一放在标题中部（`第N次更新 | 日期`），不要写成 `日期 第N次更新`。

## 五、正文结构（精简优先）

> **原则**：每次更新内容可能很多，**不要写得太详细**。标题写「时间 + 更新内容」，下面用**一行灰色小字**列举 2-3 个重点；只有重要更新才在上方详写。

固定顺序：

1. **标题行下方紧跟一行灰色小字重点**（用引用块）：
   ```
   > 重点：A；B；C
   ```
   viewer 会把它渲染为灰色小字，作为抽屉里的速读摘要（`getUpdateSummary` 会跳过 `>` 行，不会污染自动摘要）。
2. **`## 📌 必看清单`**（注意：章节名含 📌，这是 `convert.py` 的解析锚点，**不可改名**）。
   每条：`- [N · 标签] [[slug]] — 一句话`。N 取 1-5，与 importance 同体系；标签按上表（必看/重要/有价值/常规/次要）。无必看项写 `无`。
3. **`## 新增页面` / `## 更新页面` / `## 观点变化`**（这三个章节名也是解析锚点，不可改名）。
   每条：`- [[slug]] — 简述`。这些章节决定侧边栏 severity 标签（新增 / 更新 / 观点改变）。
   若某节无内容，写 `无`，不要删节（删节会导致该页在「恢复标签」时不被标记）。
4. 可选 **`## 概览`**：简述规模（处理素材数、新增 / 更新页数），仅重要更新写。

## 六、与 viewer 功能的对应关系

| 源文件要素 | viewer 表现 |
|---|---|
| 必看清单 `[N · ...]` 分数 | 首页「近期更新」卡片徽章 + 抽屉内等级徽章 |
| 新增 / 更新 / 观点变化章节 | 「🏷 恢复此更新的标签」把 severity 标签打到侧边栏文件树 |
| 标题 + 灰色小字 | 抽屉记录卡顶部标题与摘要 |
| 本页被更新记录影响 | 文章内「页面更新历史」按钮计数；点开见每条的「查看快照 / 对比当前」 |

- **恢复标签**：全局抽屉每条均有「🏷 恢复此更新的标签」按钮，点击恢复该次更新的 severity 标签到侧边栏。
- **对照（快照）**：本页历史里每条更新有「查看快照 / 对比当前」，依赖该页 git 历史；无快照时按钮**置灰显示**并提示「该页面暂无历史快照」，不凭空消失。

## 八、机器可读约束（给脚本 / 维护者）

- frontmatter 的 `importance` 必须是 1-5 的整数串；`更新类型` 必须是四枚举之一。
- 章节名固定：`## 📌 必看清单`、`## 新增页面`、`## 更新页面`、`## 观点变化`。
- 标题行必须含 `第N次更新` 与 ISO 日期，便于 `getUpdateNum` / 排序解析。
- 批量归一脚本：`scripts/normalize_update_records.py`（仅改格式，不动语义）。
